# 人手不足研究所｜01 情報設計書 v1.0
**文書名:** 01-information-architecture.md
 **対象サイト:** 人手不足研究所
 **位置づけ:** 00 基本設計書の下位設計書
 **目的:** サイト内のコンテンツ分類・関連付け・一覧生成・将来的なSEOランディングページ生成の基本ルールを定義する。

# 1. 情報設計の目的
人手不足研究所は、建設・介護・物流・製造・宿泊など、人手不足の影響を受ける企業に対して、採用、人事・組織、業務改善、DX、IT活用などを横断的に扱う。

そのため、WordPress等で一般的な、

「1記事を1つのカテゴリ階層に所属させる」

という考え方を基本としない。

各コンテンツに複数の属性を付与し、**同じコンテンツを複数の文脈から発見できる情報構造**を構築する。

基本となる分類軸は以下の5つとする。

- **テーマ**
- **業界**
- **職種**
- **地域**
- **コンテンツ形式**

これらは原則として独立した属性として管理する。

# 2. 情報設計の基本思想
## 2-1. 「階層」ではなく「属性」で管理する
例えば、

建設 ＞ 現場作業員 ＞ 採用 ＞ 北陸

という固定階層は作らない。

代わりに、1つのコンテンツが以下の属性を持つ。

themes:

  - recruiting

industries:

  - construction

jobs:

  - construction-worker

areas:

  - hokuriku

contentType: report

これにより同じコンテンツを、

- 建設についての記事
- 現場作業員についての記事
- 採用についての記事
- 北陸についての記事
- レポート

のすべてとして扱えるようにする。

# 4. ブランド分類とSEO分類を分離する
サイトでは、

採る
 活かす
 減らす
 強くする

というブランド表現を使用できる。

ただし、これをデータ上の主要カテゴリ名にはしない。

SEO・情報検索上は、

採用・人材確保
 組織・人事・定着
 業務改善・DX
 経営改善・IT活用

を使用する。

つまり、

**ブランド言語 = 読者に思想を伝えるもの**

**情報分類 = コンテンツを正確に整理するもの**

として分離する。

# 5. テーマの複数付与
テーマは複数付与を許可する。

例えば、

「Excelによる勤怠管理を改善したことで管理職の残業が減った建設会社」

であれば、

themes:

  - dx

  - organization

のように複数テーマに関連する可能性がある。

ただし、すべてのコンテンツには原則として**primaryThemeを1つ設定する。**

primaryTheme: dx

themes:

  - dx

  - organization

primaryThemeは、

- パンくず
- 関連記事
- SEO上の主要文脈
- UI表示

などに利用する。

# 7. 業界はカテゴリ階層にしない
例えば、

建設

 ├ 採用

 ├ DX

 └ 人事

という固定構造にはしない。

建設は、

industries:

  - construction

という属性として管理する。

これにより、

**建設 × 採用**

**建設 × 人事**

**建設 × DX**

などを必要に応じて抽出できる。

# 8. 業界の複数付与
業界横断コンテンツでは複数業界を付与できる。

例：

「建設・物流・介護の人手不足率を比較」

industries:

  - construction

  - logistics

  - nursing-care

業界全体を扱う場合は、

industries:

  - cross-industry

など専用属性を使用する。

# 10. 業界と職種の関係
業界と職種には関連性があるが、**データ構造上の固定親子関係にはしない。**

例えば「事務」は、

- 建設
- 介護
- 物流
- 製造
- 宿泊

のすべてに存在する可能性がある。

したがって、

建設

 └ 事務

ではなく、

industry: construction

job: office-worker

として独立管理する。

# 11. UI上では業界と職種を関連付ける
データ上は独立していても、ユーザー体験上は関連職種を表示してよい。

例：

### 建設の記事を探す
- 現場作業員
- 施工管理
- 設計
- 営業
- 事務

### 介護の記事を探す
- 介護職
- ケアマネジャー
- 看護職
- 施設長

この関連情報は別途マスターデータとして保持する。

# 12. 地域
地域は地理的な対象を示す属性。

基本階層として、

全国

地域ブロック

都道府県

を持つ。

地域ブロック例：

- 北海道
- 東北
- 関東
- 北陸
- 甲信越
- 東海
- 関西
- 中国
- 四国
- 九州・沖縄

必要に応じて都道府県を設定する。

# 13. 地域の複数付与
例えば、

富山・石川・福井の建設業採用比較

なら、

areas:

  - toyama

  - ishikawa

  - fukui

  - hokuriku

を許可する。

ただし、地域階層を利用して上位地域を自動推論できる場合は、重複入力を避ける設計も検討する。

これは03コンテンツモデル仕様書で最終決定する。

# 14. コンテンツ形式
**「何について書かれているか」ではなく「どのようなコンテンツなのか」**を示す。

初期形式：

### 調査・レポート
独自調査、公的データ分析、アンケート等。

### インタビュー
企業、経営者、従業員、専門家、支援会社等への取材。

### 解説
テーマについて体系的に説明する記事。

### 事例
具体的な企業やプロジェクトの取り組み。

### ニュース・動向
法改正、市場動向、新技術等。

# 15. レポートは重要なコンテンツ形式とする
人手不足研究所では、**調査・レポートをブランドの中心的コンテンツ**として扱う。

レポートは単なるPDFダウンロードページではなく、

- 調査概要
- 主要データ
- グラフ
- 考察
- 一部結果
- 関連記事
- PDFダウンロード

を持つWebページとして構築する。

検索流入・被リンク・AI引用・リード獲得の中心資産とする。

# 16. 「タグ」をさらに細分化する
5つの主要分類とは別に、細かなテーマを表す補助タグを持つ。

例：

Indeed

求人ボックス

採用単価

若手

外国人材

生成AI

Excel

SaaS

給与

評価制度

離職

オンボーディング

予約システム

補助タグは記事探索・関連記事生成に利用する。

ただし、すべてのタグについてSEO一覧ページを生成しない。

# 17. 分類と公開ページを分離する
本設計の重要原則として、

**属性として存在することと、公開ランディングページを持つことは別**

とする。

例えば、

area: toyama

という記事が1本あっても、

/areas/toyama/

を自動的にSEOページとして公開する必要はない。

# 18. SEOランディングページ化の考え方
以下を満たす属性について、一覧ページ・ランディングページ化を検討する。

### 基準
- 十分な関連コンテンツがある
- 独自の説明文を書ける
- 明確な検索需要がある
- 他ページと検索意図が重複しない
- 継続的に更新できる
- ユーザーに一覧ページとして価値がある

単純な記事一覧だけの薄いページは原則作らない。

# 19. 初期段階で公開する分類ページ
初期は以下を優先する。

### テーマ
- 採用・人材確保
- 組織・人事・定着
- 業務改善・DX
- 経営改善・IT活用

### 業界
コンテンツが十分蓄積したものから公開。

初期最優先：

**建設**

その後：

- 介護
- 物流
- 製造
- 宿泊

### コンテンツ形式
- 調査・レポート
- インタビュー

を特に重要視する。

# 20. 初期段階では公開しない可能性が高いもの
以下は属性として保持するが、記事数が少ない段階では独立ページを作らない。

- 細かな職種ページ
- 都道府県ページ
- 細かな補助タグページ
- 業界×テーマページ
- 業界×職種ページ
- 地域×業界ページ
- 職種×テーマページ

コンテンツ蓄積後にSEO価値を判断して生成する。

# 21. 組み合わせページ
将来的には、

建設 × 採用

介護 × 定着

物流 × DX

北陸 × 建設

建設 × 現場作業員

宿泊 × 予約システム

などの組み合わせページを生成できる設計にする。

ただし、組み合わせページを機械的に大量生成しない。

**コンテンツ量・検索需要・独自価値を確認したものだけを公開する。**

# 23. 関連記事の生成
関連記事は単純な「同じカテゴリ」だけで生成しない。

以下の一致度を利用する。

優先順位例：

- 同一業界
- 同一テーマ
- 同一職種
- 同一地域
- 同一タグ
- 同一コンテンツ形式

複数条件が一致する記事ほど関連度を高くする。

具体的なスコアリングは技術設計書で定義する。

# 24. レポートと関連記事の関係
レポートをコンテンツクラスターの中心に置ける構造とする。

例えば、

### 建設業人手不足レポート2026
を中心として、

建設業は本当に人手不足なのか

↓

建設技能者は20年でどれくらい減った？

↓

若手技能者はなぜ増えない？

↓

建設業の採用単価

↓

現場職が転職時に見るポイント

↓

建設会社インタビュー

などを関連付ける。

各記事から中心レポートへ内部リンクし、レポートから各詳細記事へもリンクする。

# 25. インタビューの分類
インタビューは対象者属性も別途持つ。

例：

intervieweeType:

  - company

候補：

- company
- executive
- hr
- employee
- recruitment-support
- hr-consultant
- it-vendor
- expert

これにより、

**建設会社インタビュー**

**採用支援会社インタビュー**

**働く人インタビュー**

などを抽出できる。

# 26. 調査・レポートの分類
レポートには調査種別を持たせる。

例：

researchType:

  - statistical-analysis

候補：

- statistical-analysis
- survey
- interview-research
- market-research
- case-analysis

複数方式を組み合わせる場合は複数付与を許可する。

# 27. タグ命名ルール
内部IDは原則として、

- 英小文字
- kebab-case
- 原則として英語

を使用する。

例：

construction

nursing-care

logistics

manufacturing

hospitality

construction-worker

site-manager

truck-driver

recruiting

organization

dx

management

ユーザーに表示する日本語ラベルとは分離する。

# 28. タグマスター
各属性は記事内に自由入力せず、原則としてマスターから選択する。

例：

id: construction

label: 建設

type: industry

description: 建設業に関するコンテンツ

これにより、

「建設」
 「建設業」
 「建築・建設」

など表記揺れが発生するのを防ぐ。

# 29. 新しい分類の追加ルール
新しい業界・職種・地域・タグを追加する場合、

- 既存タグで表現できないか確認
- 今後複数記事で使用する可能性があるか確認
- 同義語が存在しないか確認
- IDを決定
- 表示名を決定
- 必要に応じて説明文を作成

の順で追加する。

記事ごとに場当たり的なタグを増やさない。

# 30. ナビゲーションとの関係
グローバルナビゲーションと情報分類は一致させる必要はない。

例えばヘッダーには、

**調査・レポート**

**採用・人材確保**

**組織・人事**

**業務改善・DX**

**インタビュー**

**人手不足研究所について**

を表示する。

一方で裏側では、

業界・職種・地域・タグ等の多面的な属性を保持する。

つまり、

**ナビゲーションは人間のため**

**分類データは検索・関連付け・拡張のため**

と考える。

# 31. サイト内検索
将来的なサイト内検索では、

- キーワード
- テーマ
- 業界
- 職種
- 地域
- コンテンツ形式

で絞り込める構造を想定する。

ただし初期リリースで高度な検索機能を必須としない。

# 32. SEO/AIOとの関係
情報分類そのものをSEO目的で乱造しない。

人手不足研究所では、

**独自調査**
 **一次情報**
 **専門的な解説**
 **明確な著者情報**
 **出典**
 **更新履歴**
 **関連コンテンツ**

を重視する。

分類情報は、

- 検索エンジンがサイトの専門領域を理解する
- AIがコンテンツ同士の関係を理解しやすくする
- ユーザーが関連情報を探索する

ための基盤として利用する。

# 33. 情報設計上の禁止事項
以下は原則禁止する。

### 1. 1記事1カテゴリに固定する
多面的な分類を阻害するため。

### 2. 業界と職種を固定親子にする
複数業界にまたがる職種が存在するため。

### 3. タグを自由入力する
表記揺れ・重複を防ぐため。

### 4. すべてのタグページを自動公開する
薄いページの大量生成を防ぐため。

### 5. 組み合わせページを自動生成する
SEO目的だけの低価値ページを防ぐため。

### 6. URLを分類変更に依存させすぎる
後からテーマ変更等が発生してもURLを維持できるようにするため。

# 34. 本設計の中心原則
人手不足研究所の情報設計は、

**テーマ × 業界 × 職種 × 地域 × 形式**

の5軸を基本とする。

ただし、

**5軸 = URL階層**

ではない。

5軸はあくまでコンテンツの意味を表現するメタデータであり、

**URL**
 **ナビゲーション**
 **SEOランディングページ**
 **関連記事**
 **サイト内検索**

は、このデータを目的に応じて利用する。

# 35. 将来的な情報構造
コンテンツが蓄積すると、例えば以下のような情報探索が可能になる。

### 業界から
**建設**
 → 採用
 → 組織
 → DX
 → レポート
 → インタビュー

### 課題から
**採用**
 → 建設
 → 介護
 → 物流
 → 製造
 → 宿泊

### 職種から
**ドライバー**
 → 採用
 → 給与
 → 定着
 → 業務改善

### 地域から
**北陸**
 → 建設
 → 物流
 → 製造

# 38. Claude Codeへの実装上の指示
Claude Codeは、本設計書における分類を**固定されたページ階層として解釈してはならない。**

実装時には、

Content

 ├ Theme

 ├ Industry

 ├ Job

 ├ Area

 └ Content Type

という多対多の属性関係を基本とする。

業界・職種・テーマ等の追加によって記事本体のコード変更が発生しない構造を優先する。

また、新しい属性値を追加する際にはマスターデータを更新する方式とし、記事ファイル内で未定義の分類値を自由入力できないよう、可能な範囲で型・validationによって制御する。

この制約は指示文ではなく仕組みで担保する。

- 分類の禁止事項（1記事1カテゴリ固定、業界と職種の親子化、タグ自由入力、組み合わせページ自動生成）は `.claude/rules/taxonomy.md` に記述し、常時読み込ませる
- 実際の防御はZod validationとビルド失敗で行う。Claude Codeが未定義IDを使ったとしても `npm run build` が落ちる状態にする
- ルールに書くのは「なぜそうするか」、validationに書くのは「何を許さないか」とし、両方に同じ内容を二重管理しない

## 39. この設計で実現したい状態
例えば将来「北海道の宿泊業で、フロントスタッフの採用と予約業務DXについて調査したレポート」を公開するときも、サイト構造を変更せず、

primaryTheme: recruiting

themes:

  - recruiting

  - dx

  - management

industries:

  - hospitality

jobs:

  - hotel-front-desk

  - reservation-management

areas:

  - hokkaido

contentType: report

と追加するだけで、

**宿泊**
 **北海道**
 **採用**
 **DX**
 **フロント**
 **レポート**

という複数の入口から同じ情報へ到達できる。

これを人手不足研究所の情報アーキテクチャにおける完成形とする。
