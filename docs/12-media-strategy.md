# 人手不足研究所｜12 メディア戦略 v1.0

**文書名:** 12-media-strategy.md
**対象サイト:** 人手不足研究所
**位置づけ:** 00〜11の前提となる事業・競合・チャネル・運用体制の判断を定義する上位文書
**目的:** 「なぜこのメディアが読まれ、なぜ他のメディアではなく人手不足研究所が引用されるのか」を明文化し、コンテンツ判断とチャネル判断の基準にする。

00は「何を作るか」、04は「どう検索されるか」を定義している。本書は **「誰と戦い、どこで勝つか」** を定義する。

---

# 1. 前提となる決定事項

| 項目 | 決定 |
| --- | --- |
| 独立性 | 人手不足研究所は独自ドメインの独立メディアとする。新規事業開発ノートのサブカテゴリにしない |
| 既存記事 | bizdev-note.com の採用・人手不足系記事は人手不足研究所へ移設する（301） |
| 新規事業開発ノート | 新規事業・創業をテーマとするメディアとして継続する。人事・採用テーマは扱わない |
| 運用 | Claude を編集・制作・検証のパートナーとして常時使う前提で設計する |

## 1-1. 2メディアの棲み分け

| | 新規事業開発ノート | 人手不足研究所 |
| --- | --- | --- |
| テーマ | 新規事業・創業 | 人手不足（採用・組織・業務・IT） |
| 読者 | 事業を作る人 | 人が足りない会社の経営者・管理部門 |
| コンテンツ形式 | 解説・実践記録 | 調査・レポート・インタビュー |
| 役割 | 既存資産・被リンク元 | 事業接点の主戦場 |

テーマが重なる記事を両方に置かない。境界が曖昧な場合、「人が足りないことが主題か」で判定する。

相互リンクは張ってよい。ただし「姉妹メディア」としての導線は控えめにする。読者にとって関係が分からない2サイトを並べても、信頼にはつながらない。

# 2. 競合環境

## 2-1. 既に存在するプレイヤー

| 区分 | 例 | 強み | 構造的な限界 |
| --- | --- | --- | --- |
| 大手調査機関 | パーソル総合研究所、帝国データバンク、リクルート系 | 大規模調査、権威性、報道での引用 | マクロ。個社の具体策には降りてこない |
| SaaSベンダーのオウンドメディア | 現場改善ラボ（Tebiki）、各種HR SaaS | 会員規模、ウェビナー動員、予算 | 自社プロダクトへの誘導が最終目的。中立ではない |
| 建設特化の実務メディア | 現場ラボ、建設ITラボ | 現場経験に基づく具体性 | 施工管理・教育・ツール導入が中心。採用〜組織〜経営の横断は薄い |
| 人材会社・媒体のコラム | 各社 | SEO物量 | 自社サービスの手前まで。一次情報が薄い |

## 2-2. 勝てない土俵

以下では正面から戦わない。

- **調査規模** — 数千サンプルの定量調査で大手と競わない
- **コンテンツ物量** — SEO記事の本数で人材会社と競わない
- **動員力** — 大規模ウェビナーの集客数で SaaS ベンダーと競わない

## 2-3. 空いている位置

上記の裏返しとして、以下が空いている。

**「人手不足を採用問題に閉じず、業務量とITまで含めて扱う、中小企業向けの中立な調査メディア」**

具体的には3点。

### (1) 課題の横断

大半のメディアは「採用」か「DX」のどちらかに寄っている。人手不足研究所は00で定義した **採る／活かす／減らす／強くする** を循環として扱う。

「人が採れない」の答えが「業務を減らす」であることは実務では珍しくないが、採用メディアはそれを書けない。ここが構造的な差になる。

### (2) 支援側の視点

企業インタビューだけでなく、**採用支援会社・社労士・IT会社・DX会社への取材**を初期から対象に含める（01 §25、04 §20）。

これは他メディアがやりにくい。SaaSベンダーのメディアは競合になり得る支援会社を取材できず、人材会社のメディアも同様。中立な立場だからできる。

### (3) 中小企業の具体性

大手調査が扱わない、従業員数十名規模の会社が実際に何をしたかを記録する。成功事例に限定せず、試行錯誤中の状態も扱う（10 §23）。

## 2-4. 差別化の言語化

一言でいうと以下。About と Report の冒頭で繰り返し使う。

> 統計は大手が出している。人手不足研究所が出すのは、**その統計の下で実際に何が起きていて、中小企業が何を試したか** である。

小規模調査を「サンプル数が少ない」と受け取られないための予防でもある。サンプル数で勝負していないことを最初から明示する。

# 3. コンテンツの資産構造

## 3-1. 3層で考える

| 層 | 中身 | 目的 | 増やし方 |
| --- | --- | --- | --- |
| **一次情報層** | インタビュー、独自アンケート、実務での観察 | 他が持っていない情報 | 取材。時間がかかる。これが堀 |
| **分析層** | Report、統計の独自分析 | 引用・被リンク・リード | 一次情報＋公的統計。Claudeの支援効果が最も大きい |
| **検索層** | Article、テーマハブ、業界ハブ | 検索流入 | 分析層から論点を分解して生成 |

一次情報層 → 分析層 → 検索層 の順で作る。逆順（検索層から作る）にすると、量産型メディアと区別がつかなくなる。

## 3-2. コンテンツの再利用

1回のインタビューから以下を生む（10 §74）。

```
Interview 1件
  ├─ Interview記事
  ├─ Article 2〜3本（論点を分解）
  ├─ Report の1章
  ├─ 引用・数値（他記事から参照）
  ├─ メルマガ 1〜2通
  └─ 次の取材候補（言及された取引先・支援会社）
```

取材を「記事1本のための取材」と考えると採算が合わない。**1件の取材が何本に化けるか**で計画する。

## 3-3. 建設に絞る理由と、絞りを解く条件

初期は建設のみ（00 §15、10 §9）。理由は既存の調査素材があることに加え、**「建設に強い」と言えるまでは他業界に広げても専門性が薄まるだけ**であるため。

絞りを解く条件：

- 建設の Article が10本以上、Report が2本以上、Interview が5件以上
- 建設関連の検索流入が発生している
- 建設の取材ネットワークから他業界への紹介が発生している

本数ではなく「建設で指名される状態」を条件とする。

# 4. チャネル戦略

## 4-1. チャネルの役割

| チャネル | 役割 | 開始時期 |
| --- | --- | --- |
| 自然検索 | 中長期の主力。Report・Article | 公開直後から仕込み、成果は数ヶ月後 |
| メール | **初期の主力**。既存リストへの配信 | 公開直後 |
| 取材（アウトバウンド） | 一次情報の獲得。同時に認知 | 公開直後 |
| note | リファラル。本文は自サイト、noteは要約＋誘導 | Article 3本以降 |
| SNS | 補助。Interview公開時の告知 | Interview 1件目以降 |
| 被リンク | Report経由で自然発生を狙う | Report 2本目以降 |

## 4-2. 初期はメールが主力になる

公開直後の自然検索流入はゼロに近い。一方で、既に到達可能なリストがある。

- 新規事業開発ノート経由のリスト
- 社労士相談ドットコムのリスト（企業側リスト）

**まずレポート・記事を配信し、反応した企業へ取材を打診する**という順番が、いきなり取材依頼を送るより成立率が高い。相手から見て「知らないメディアからの取材依頼」ではなく「読んだことのあるメディアからの取材依頼」になる。

この方針は 10 §33 の「候補企業抽出 → 企業調査 → メール（取材打診）」を置き換える。10 §33-34 を以下に読み替える。

```
配信リストへレポート・記事を配信
  ↓
反応（開封・クリック・DL）した企業を抽出
  ↓
企業調査
  ↓
取材打診
  ↓
反応がない層に対しては、従来通りコールドで打診（少数ずつ検証）
```

この結果、10 §41 の取材営業開始条件に **メール配信基盤とリスト整備** が加わる。Phase 6 のフォーム実装だけでは不足する。

## 4-3. noteの扱い

本体は独自ドメイン。noteは要約と誘導のみに使う。note側に本文を全文置くと、自サイトの検索資産が育たない。

## 4-4. 被リンクの作り方

営業的なリンク獲得はしない（04 §73）。代わりに、引用されやすい形を作る。

- Report に「調査名／調査主体／調査年／URL」を明示し、引用しやすくする
- グラフを画像として単体で引用できる状態にする（出典クレジットを画像内に入れる）
- 取材企業が自社サイト・SNSで紹介しやすいよう、公開時に共有用URLと文面案を渡す

# 5. 事業への接続

## 5-1. メディアの役割は3つ

| 役割 | 内容 |
| --- | --- |
| リード獲得 | Report DL → サービス相談 |
| 市場理解 | 取材そのものが市場調査。何に困り、何にお金を払っているか |
| 信頼形成 | 「調査しているメディアの運営者」という立場が、営業時の前提を変える |

3番目が過小評価されやすい。人手不足研究所の運営実績は、採用支援・サイト制作・業務改善の提案時に、実績資料そのものとして機能する。

## 5-2. 収益化の段階

```
Stage 1  メディア運営（収益なし）
Stage 2  取材・調査から市場理解 → 個別の受託（採用支援・サイト制作・業務改善・IT）
Stage 3  複数社で共通する課題 → パッケージ化したサービス
Stage 4  （検討）媒体としての収益 — 広告掲載、タイアップ、共同調査
```

Stage 4 は、現場改善ラボが会員数十万規模で広告媒体として販売している領域。同じ規模を目指す必要はないが、**建設業の中小企業に絞った媒体**としてなら成立する可能性がある。ただし Stage 2-3 が先。

初期段階でタイアップ記事を受けない。中立性が差別化の根拠であるため（2-3参照）。

## 5-3. 取材と営業を混同しない

10 §55-56 の原則を維持する。取材時にサービスを売り込まない。

ただし、取材の中で相手から相談が出た場合は対応してよい。この境界を運営側で明確に持っておく。

# 6. 既存資産の移行

## 6-1. 移行対象

bizdev-note.com に公開済みの採用・人手不足系記事。現時点の該当は建設業の採用市場・人手不足をテーマとした記事。

## 6-2. 移行手順

1. 移行対象記事の一覧を作る（URL・タイトル・公開日・被リンクの有無）
2. 新URLを決める（02 §42-2 の命名規則に従う）
3. Content Model（03）に合わせて frontmatter を付け直す
4. 本文を人手不足研究所の文脈に合わせて調整する
   - 新規事業開発ノート固有の言及を削除
   - テーマハブ・Report・業界ハブへの内部リンクを追加
   - 出典を `data/sources/` に登録
5. 新サイトで公開
6. 旧サイトで301リダイレクトを設定
7. 旧サイトのsitemapから削除
8. 旧サイト内の内部リンクを新URLへ張り替え
9. Search Console で両ドメインを確認

## 6-3. 移行時の注意

- **旧サイトに記事を残さない。** 「念のため残しておく」が最も避けるべき状態。自サイト間で検索意図が競合する
- 移行と同時に大幅リライトしない。まず同じ内容で移し、301が効いていることを確認してから改稿する。問題が起きたときの切り分けができなくなる
- 被リンクを受けている記事は、301後に元のリンク元へ連絡するか検討する

# 7. 運用体制

## 7-1. 前提

実質一人運用。Claudeを制作・検証のパートナーとして使う。この前提を計画に反映する。

## 7-2. 人間しかできないこと

Claudeに委譲できない。ここに時間を使う。

- 取材の打診・実施・関係構築
- 何を調べるかの決定
- 企業評価・掲載判断
- 事実確認（数値・企業情報・引用）
- ブランド・編集方針の判断

## 7-3. Claudeに任せる領域

| 作業 | 使い方 |
| --- | --- |
| 記事構成の設計 | 取材メモ・統計を渡して構成案を出させる |
| 初稿執筆 | 構成確定後。一次情報は必ず人間が供給する |
| 統計の整理・比較 | 複数統計の突き合わせ、経年比較の下ごしらえ |
| 内部リンクの提案 | 既存コンテンツ一覧を渡して関連付けを出させる |
| frontmatter・taxonomy | `/add-article` 等のスキル |
| 整合チェック・QA | `/qa`、validation |
| 取材前の企業調査 | 公開情報の整理 |
| メール文面のドラフト | 配信・打診の文面 |

サイト構築は Claude Code、コンテンツ制作・調査は Claude（チャット／Cowork）と使い分ける。

## 7-4. 現実的な制作ペース

以下を初期の想定値として置く。実測で更新する。

| 成果物 | 想定工数（Claude併用） |
| --- | --- |
| Article（既存素材から） | 3〜5時間 |
| Article（新規調査を伴う） | 8〜12時間 |
| Interview 1件（打診〜公開） | 10〜15時間 |
| Report 1本 | 30〜50時間 |

月あたりの想定：

- Article 2〜3本
- Interview 1件
- Report 四半期に1本

**この水準を下回る計画を立てない。** 10 §75 が「取材数を重要指標とする」としているのに対し、具体値がなかったため本書で置く。

## 7-5. 更新が止まるリスクへの備え

一人運用の最大のリスクは更新停止。以下で緩和する。

- 記事を「連載」の体裁にしない。定期公開の約束をしない
- 公開日をコンテンツ内に約束として書かない
- 常に2〜3本のドラフトを持っておく。ゼロから書き始める状態を作らない
- 取材が止まっても、統計分析型の Article は単独で作れる。この経路を常に確保しておく

# 8. 段階と判断基準

| Stage | 状態 | 次へ進む条件 |
| --- | --- | --- |
| 1 | メディアが存在し、取材依頼を出せる | Article 1〜3本、Report 1本、About、取材募集ページ |
| 2 | 取材が成立する | Interview 1件公開 |
| 3 | 一次情報からコンテンツが生まれる | Interview → Article への展開が2回以上 |
| 4 | 検索流入が発生する | 非指名クエリでの流入が継続的に発生 |
| 5 | リードが発生する | Report DL が月数件、うち対象業界が過半 |
| 6 | 市場理解が蓄積する | 複数社から同一課題が出る |
| 7 | サービスに接続する | メディア経由の受託が発生 |

各Stageで見る指標は 10 §76-77 に従う。**Stage 4 より前に PV を主要指標にしない。**

# 9. やらないこと

戦略上、明示的に選ばない選択肢。

- SEO記事の量産による集客
- タイアップ記事・広告記事（Stage 3 まで）
- 業界を広げる（建設で指名されるまで）
- 定期連載の約束
- 大規模調査での正面勝負
- note や SNS を本体にする
- 取材を営業の口実に使う
