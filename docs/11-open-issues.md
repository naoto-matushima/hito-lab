## A-5. data/ ディレクトリ構成の不一致

| 03 §70 | 08 §16 |
| --- | --- |
| people / companies / ctas / sources / taxonomies / assets / forms | themes / industries / occupations / companies / authors / ctas / forms |

03は `taxonomies/` 配下に分類をまとめ、08は分類を個別ディレクトリに展開している。また08には `sources/` と `assets/` が無く、03の `people/` が08では `authors/` になっている。

**推奨：** 03を正とし、08 §16・§116を以下へ修正する。

```
data/
├─ taxonomies/   themes / industries / jobs / areas / tags
├─ people/
├─ companies/
├─ sources/
├─ ctas/
├─ forms/
└─ assets/
```

`authors` ではなく `people` とする理由は、03 §19が著者・編集者・監修者・インタビュー対象者を同一マスターで扱うと定義しているため。

## A-6. Report Masterの定義漏れ

08 §30・§99が「Report Master」を前提としているが、03にReport Masterの定義がない。03にあるのはReport（コンテンツモデル）、Asset Master、Form Masterの3つ。

**推奨：** Report Masterという概念を追加せず、08 §30の記述を「Report frontmatterの `download.assetId` 経由でAsset Masterを参照する」に修正する。マスターを増やさない。

# B. 未確定の設計判断（人間が決めるべきこと）

Claude Codeに決めさせない。実装着手前に確定させる。

## B-1. 取材募集・サービス相談ページのURL

07 §60が `/interview-request/` と `/interviews/apply/` を併記、§62が `/consultation/` を「作成可能とする」に留めている。09・10は `/interview-request/` を使用。

**決めること：** 4つのCVページのURLを確定する。公開後の変更コストが高いため、実装前に決める。

## B-2. Chartの実装方式

06 §43-45がChartを主要なブランド資産と位置づけ、08 §20がChartをComponent化するとしている。一方で08 §7-8は静的生成優先・JavaScript最小化を原則としている。インタラクティブChartはClient Componentとなり、この原則と衝突する。

**選択肢：**

| 方式 | 利点 | 欠点 |
| --- | --- | --- |
| サーバー生成SVG | JS不要。LCP有利。テキストとして構造化データに載る | インタラクションなし。実装工数中 |
| 画像（事前生成PNG/WebP） | 実装最小。既存のmatplotlibワークフローを流用可 | 数値がテキストにならず、AIO方針（04 §58）と衝突。alt/本文での補完必須 |
| Recharts等のClient Component | 実装容易。表現力が高い | JS増。静的生成優先の原則と衝突 |

**推奨：** サーバー生成SVG。04 §58が「重要数値・結論はテキストでも記述する」としており、SVG内テキストが機械可読である点が方針と最も整合する。ただし工数はPhase 3で確認する。

## B-3. Report PDFの配布方式

08 §29-31がフォーム経由の配布を前提としつつ、Phase 1ではPublic Blobを想定している。この場合、PDFのURLを知っていればフォームを通さず取得できる。

**決めること：** Phase 1で Signed URL を実装するか、名前解決困難なパスによる実質的な保護で妥協するか。後者を選ぶ場合、その判断を明記する（後から「守られていたはず」と誤認しないため）。

## B-4. メール配信同意の扱い

07 §51が「必要に応じて別同意を検討」に留めている。一方、10 §50の成長モデルはReport DL → 関係構築 → 取材という循環を前提としており、DL者へのメール送付が事実上の前提になっている。

**決めること：** Report DLフォームに「人手不足研究所から関連情報を受け取る」のチェックボックスをPhase 1から入れるか。後から同意を取り直すのは難しいため、初期から入れることを推奨する。

## B-5. 個人情報の保持期間

07 §80が「運用開始前に定める」としたまま未確定。Privacy Policy公開が09 §66のLaunch条件に含まれるため、Phase 9より前に決まっている必要がある。

## B-6. 年次Reportのバージョニング

02 §39が「年号ありURL」と「年号なしURLで内容更新」の両方を認め、「シリーズ単位で統一する」としている。04 §64は年度別保持を推奨。建設業人手不足レポートをどちらにするか未確定。

**推奨：** 建設業人手不足レポートは年号あり（`/reports/construction-labor-shortage-2026/`）。理由は、翌年版を出したときに前年版が独立した被リンク資産として残るため。

# C. 設計書で扱われていない論点

00〜10に該当する記述がなく、追加検討が必要な項目。

## C-1. 既存メディア（新規事業開発ノート）との関係 ✅ 決定済み

現在、bizdev-note.com に建設業の採用市場・人手不足をテーマとした記事が既に公開されている。人手不足研究所の初期Article（10 §12「建設業は本当に人手不足なのか」）と主題が重なる。

**論点：**

- 既存記事を人手不足研究所へ移設するのか、両立させるのか
- 移設する場合、301リダイレクトを設定するのか
- 両立させる場合、検索意図の重複をどう回避するのか（04 §67「1検索意図1代表ページ」との整合）
- ドメイン・サイト名の関係をAboutでどう説明するのか

**決定：** 人手不足研究所は独自ドメインの独立メディアとする。既存の採用・人手不足系記事は移設し、旧URLから301リダイレクトする。旧サイトには残さない。新規事業開発ノートは新規事業・創業テーマのメディアとして継続し、人事・採用テーマは扱わない。

手順は 12 §6、リダイレクト仕様は 02 §42-2 を参照。

残る作業：移行対象記事の一覧作成（URL・タイトル・被リンクの有無）と新URLの確定。

## C-2. 競合メディアのポジショニング ✅ 決定済み

現場ラボ・現場改善ラボなど、建設業の人手不足・DXを扱うメディアが既に存在する。また「人手不足」領域の検索結果はパーソル総合研究所、帝国データバンク、ミイダス等の大手が調査データで上位を占めている。

04は自サイトのSEO方針を定義しているが、競合が既に押さえている領域と、そこに対してどう差別化するかの記述がない。

**決定：** 12 §2 で競合マップと差別化軸を定義した。勝てない土俵（調査規模・コンテンツ物量・動員力）を明示し、空いている位置を「人手不足を採用問題に閉じず、業務量とITまで含めて扱う、中小企業向けの中立な調査メディア」とした。

About・Reportの冒頭で使う表現も 12 §2-4 に定めた。

## C-3. 「研究所」というネーミングの検討

現時点で「人手不足研究所」という名称の既存事業体は確認できなかったが、パーソル総合研究所・人材マネジメント研究所など、同じ意味空間に「◯◯研究所」が複数存在する。指名検索での識別性と、レポート引用時の権威性の両面で影響する。

**論点：** ドメイン取得可否とあわせて、名称を最終確定させる。08 §116のリポジトリ名は `hito-lab` となっており、これも名称確定後に見直す。

## C-4. 運用工数の見積り ✅ 決定済み

設計書は執筆・編集・監修の3ロール、企業への公開前確認フロー、フェーズごとのQAリストを定義しているが、これを誰が何時間でこなすのかの記述がない。実質一人運用である前提が設計に反映されていない。

**論点：**

- 記事1本あたりの制作時間の想定
- 取材1件あたりの工数（打診・調整・実施・原稿・確認・公開連絡）
- 月あたり何本を維持できるか
- 維持できない場合、どのコンテンツ形式を優先して落とすか

**決定：** 12 §7 に想定工数と月次ペース（Article 2〜3本／Interview 1件／Report 四半期1本）を設定した。あわせてClaudeへの委譲範囲と、更新停止リスクへの備えを定義した。

実測が出た時点で 12 §7-4 の数値を更新する。

## C-5. 写真・ビジュアルの調達方針

06 §50がストックフォト依存を避け実写を優先するとしているが、初期はInterviewが0件であり実写が存在しない。Article Eyecatchについても06 §52が「Data Visual / Chart / Typography / Photo / Illustration から選択」としているのみ。

**論点：** Interviewが増えるまでの間、Eyecatchをどう統一するか。Report Eyecatchは06 §53でシリーズ統一フォーマットを作るとしているため、同じ発想をArticleにも適用し、テンプレート化したタイポグラフィ主体のEyecatchを生成する方式が現実的。

## C-6. 取材アプローチの初手 ✅ 決定済み

10 §33が「候補企業抽出 → 企業調査 → 担当者特定 → メール」を初期アプローチとしている。一方で、既存の方針では建設系へのアプローチはいきなり取材打診を送るのではなく、レポート・記事のメルマガ配信から入る形を想定していた。

**決定：** メール配信を先行させる。既存リスト（新規事業開発ノート、社労士相談ドットコム）へレポート・記事を配信し、反応した企業へ取材を打診する。反応がない層に対してのみ、従来通りコールドで少数ずつ打診する。

詳細は 12 §4-2。10 §33-34 は本方針に置き換えて読む。

**影響：** 取材営業開始条件にメール配信基盤とリスト整備が加わる。Phase 6 のフォーム実装だけでは不足するため、配信手段（送信元・配信ツール・オプトアウト導線）を別途決める必要がある。これは B-4（メール配信同意）と一体で決める。

## C-7. 順位計測の手段

04 §77がSEO KPIとして「TOP10キーワード数」「カテゴリトップ順位」を挙げているが、Search Consoleの平均掲載順位以外の計測手段が定義されていない。08 §53もGA4とSearch Consoleのみ。

**論点：** 順位計測ツールを導入するか、Search Consoleの掲載順位で足りるとするか。Phase 1では後者で十分だが、KPIに「順位」と書いた以上、何で見るかを決めておく。

## C-8. 運営者情報の掲載

09 §66のLaunch条件に「Privacy公開」はあるが、運営者情報（事業者名・所在地・連絡先）の掲載要件が明示されていない。02 §35のフッターに「運営者情報」があるものの、独立ページなのかAbout内なのか未確定。

**論点：** 個人情報を取得するフォームを設置する以上、個人情報保護方針とあわせて運営者を明示する。Aboutに含めるか独立ページにするかを決める。
